01 Project goal

An end-to-end, fully automated data pipeline: extract Spotify playlist data daily, store raw in GCS, transform into normalized tables, and auto-load into Snowflake — zero manual steps after deployment. Portfolio project for data engineer / data scientist interviews. As of Session 8 the pipeline is complete end to end.

02 Architecture

Three trigger styles across the pipeline: clock (extract), event (transform), and interval-poll (Snowflake load task).

Full flow (all live): Cloud Scheduler (2 AM) → extract-spotify → GCS raw_data/to_process/ → transform-spotify (event/Eventarc) → GCS transformed_data/ → Snowflake external stage → load_spotify_task (every 5 min: COPY into staging → MERGE into final) → clean deduped warehouse tables. Extract→transform verified running autonomously 10 straight days (Aug 10–19).

★ Week 4 — Snowflake load stage

What this week accomplished

Transformed CSVs now auto-load into Snowflake, deduplicated to one current row per key, via a scheduled task using a staging + MERGE pattern. This closes the pipeline end to end.

The core problem and its solution, in one picture:

Problem: extract pulls the full playlist daily → each CSV is a near-duplicate snapshot. Loading directly stacked ~20× duplicates (measured: 3,672 rows for 180 unique songs).

GCS CSVs → COPY into STAGING (raw, all snapshots)
         → MERGE into FINAL (dedup to newest-per-key, upsert)
         → staging truncated next run

Result: MERGE collapsed 1,836 staging rows → 180 clean song rows. Re-running the task on a clean target leaves counts unchanged = idempotent (safe to run forever).

3.1 Snowflake objects created

  • Warehouse spotify_wh — XSMALL, AUTO_SUSPEND=60, AUTO_RESUME=TRUE (compute separate from storage; auto-suspend = cost control).
  • Database/schema spotify_db.raw.
  • 4 final tables — typed columns; composite PK on song_artists; release_date STRING for partial dates.
  • 4 staging tables *_staging — CREATE TRANSIENT TABLE … LIKE (transient = no fail-safe/time-travel → cheaper; correct for throwaway data).
  • Storage integration spotify_gcs_int — scoped to the transformed_data/ prefix; SA k16l50000@… granted storage.objectViewer.
  • File format spotify_csv_format — SKIP_HEADER=1, quote-enclosed (handles commas in song names).
  • External stage spotify_stage — LIST @spotify_stage proved Snowflake reads the bucket.
  • Notification integration spotify_pubsub_int — QUEUE/GCP_PUBSUB (built for the abandoned Snowpipe path).
  • Task load_spotify_task — 5-minute schedule, runs the staging+MERGE block.

3.2 The MERGE

The heart of the load — insert-or-update keyed on PK, with window-function dedup.

MERGE INTO songs t
USING (SELECT * FROM songs_staging
       QUALIFY ROW_NUMBER() OVER (PARTITION BY song_id ORDER BY added_at DESC)=1) s
ON t.song_id = s.song_id
WHEN MATCHED THEN UPDATE SET t.name=s.name, t.duration_ms=s.duration_ms, …
WHEN NOT MATCHED THEN INSERT (…) VALUES (…);
  • The QUALIFY subquery keeps only the newest row per key: partition by key, order newest-first, number the rows, keep #1. This dedups the source before merging.
  • ON = the match key ("is this song already in the final table?").
  • WHEN MATCHED → UPDATE (key exists, refresh to latest) · WHEN NOT MATCHED → INSERT (new key, add).
  • Bridge (song_artists) differs: composite match on both columns, SELECT DISTINCT (no "latest" concept), only WHEN NOT MATCHED (the two columns are the whole row).

3.3 The recurring task

load_spotify_task (5-min schedule) runs, in a BEGIN…END block: truncate staging → COPY new files into staging → four MERGEs into finals. Created suspended; activated with ALTER TASK … RESUME.

Critical: the task has NO FORCE=TRUE. It relies on COPY's load-history to skip already-loaded files, so each run ingests only new daily CSVs. FORCE=TRUE was a one-time backfill tool only — in the recurring task it would reload everything every 5 minutes and duplicate endlessly.

The idempotency proof: run the task, counts don't change — COPY finds no new files (load history), and MERGE upserts without duplicating. A pipeline you can run every 5 minutes forever without corrupting data.

⌘ Command cheat-sheet (Week 4)

Grouped by tool. Full Week 1–3 commands are in the repo's earlier TDD.

Pub/Sub (Snowpipe attempt)

Topic → bucket notification → subscription — the event bridge GCS→Snowflake.
gcloud pubsub topics create spotify-snowpipe-topic
gcloud storage buckets notifications create gs://bucket --topic=spotify-snowpipe-topic --event-types=OBJECT_FINALIZE
gcloud pubsub subscriptions create spotify-snowpipe-sub --topic=spotify-snowpipe-topic --ack-deadline=600

Snowflake — setup

Verify cloud/region right after signup (must match the bucket).
SELECT CURRENT_REGION();  -- want GCP_US_CENTRAL1
Warehouse, db, schema, tables, integration, file format, stage.
CREATE WAREHOUSE spotify_wh WAREHOUSE_SIZE='XSMALL' AUTO_SUSPEND=60 AUTO_RESUME=TRUE;
CREATE DATABASE spotify_db;  CREATE SCHEMA spotify_db.raw;
CREATE STORAGE INTEGRATION spotify_gcs_int TYPE=EXTERNAL_STAGE STORAGE_PROVIDER='GCS'
  ENABLED=TRUE STORAGE_ALLOWED_LOCATIONS=('gcs://bucket/transformed_data/');
DESC STORAGE INTEGRATION spotify_gcs_int;   -- get service account to grant
CREATE FILE FORMAT spotify_csv_format TYPE=CSV SKIP_HEADER=1 FIELD_OPTIONALLY_ENCLOSED_BY='"';
CREATE STAGE spotify_stage URL='gcs://bucket/transformed_data/'
  STORAGE_INTEGRATION=spotify_gcs_int FILE_FORMAT=spotify_csv_format;
LIST @spotify_stage;   -- proves Snowflake can read the bucket
Grant Snowflake's SA read on the bucket (GCP side).
gcloud storage buckets add-iam-policy-binding gs://bucket \
  --member="serviceAccount:k16l50000@…" --role="roles/storage.objectViewer"

Snowflake — staging + MERGE + task

Transient staging + one-time backfill (FORCE only here).
CREATE TRANSIENT TABLE songs_staging LIKE songs;
COPY INTO songs_staging FROM @spotify_stage PATTERN='.*/songs_.*\.csv' FILE_FORMAT=spotify_csv_format FORCE=TRUE;
Recurring task — no FORCE; staging→MERGE every 5 min.
CREATE OR REPLACE TASK load_spotify_task WAREHOUSE=spotify_wh SCHEDULE='5 MINUTE' AS
BEGIN
  TRUNCATE TABLE songs_staging; …
  COPY INTO songs_staging FROM @spotify_stage PATTERN='.*/songs_.*\.csv' FILE_FORMAT=spotify_csv_format;
  MERGE INTO songs t USING (…QUALIFY ROW_NUMBER()…=1) s ON t.song_id=s.song_id
    WHEN MATCHED THEN UPDATE SET … WHEN NOT MATCHED THEN INSERT …;
  …
END;
ALTER TASK load_spotify_task RESUME;
EXECUTE TASK load_spotify_task;   -- run once on demand
Verify clean + task success.
SELECT name,state,error_message FROM TABLE(information_schema.task_history())
  WHERE name='LOAD_SPOTIFY_TASK' ORDER BY scheduled_time DESC LIMIT 3;
SELECT COUNT(*) total, COUNT(DISTINCT song_id) uniq FROM songs;   -- 180 / 180

Q Doubts asked & answered

Interview revision deck. Week 4 first (newest), earlier weeks below.

Session 8 — deep-dive doubts
D1 Other GCS event types besides OBJECT_FINALIZE?›
OBJECT_FINALIZE (file created/finished — "arrived"), OBJECT_DELETE (deleted), OBJECT_METADATA_UPDATE (metadata changed, not content), OBJECT_ARCHIVE (archived / version superseded). Filtered to FINALIZE only so deletes/metadata don't wake the loader for nothing.
D2 Other event providers/types Snowflake listens to?›
Providers (cloud-agnostic): GCP_PUBSUB, AWS_SQS/AWS_SNS, AZURE_STORAGE_QUEUE/Event Grid. Flavors: inbound auto-ingest (QUEUE, INBOUND — listen for file events), outbound error notifications (push Snowpipe errors to a queue), and email notifications (task-failure alerts).
D3 What happens when AUTO_INGEST = FALSE?›
The pipe does NOT listen for events; it loads only when triggered manually via Snowflake's REST API (insertFiles). Used when your own application controls loading (upload a file, then tell Snowflake to load those specific files) rather than reacting to cloud events.
D4 What does FORCE do? (FALSE is default)›
COPY remembers every file it has loaded (load history, kept 64 days). FORCE=FALSE (default) = skip already-loaded files → re-running loads nothing (0 rows) — correct for a recurring job (only new files get in). FORCE=TRUE = ignore history, reload regardless — a one-time backfill tool. The MERGE design is immune to reloads anyway (upsert → no new duplicate row).
D5 What is a "one-time backfill"?›
Loading pre-existing historical data once to catch a table up to the present, vs ongoing loading of new data. Here: 10 days of CSVs already sat in the bucket → seed the tables once (with FORCE), then the task handles only new daily files (no FORCE). Analogy: copying a month of old letters into a new journal (backfill) vs writing tomorrow's entry (ongoing).
D6 Why QUALIFY ROW_NUMBER()…? Any other way?›
Keeps one row per key (the newest): partition by key, order newest-first, number rows, keep #1. QUALIFY filters on a window function (WHERE can't — it runs before the window computes). Alternatives: (1) subquery wrapping ROW_NUMBER + outer WHERE rn=1 (portable, no QUALIFY); (2) GROUP BY+aggregate — only for per-column maxes, not the whole newest row; (3) RANK()/DENSE_RANK() — risky: ties share a rank → duplicates; ROW_NUMBER guarantees exactly one; (4) DISTINCT — only collapses fully-identical rows (works for the bridge, not songs). Chose ROW_NUMBER for the on-ties guarantee, QUALIFY for readability.
Session 7 — Snowflake basics
Q Why a warehouse (Snowflake) vs object storage (GCS)?›
GCS stores files cheaply but has no query engine — no joins, aggregations, or types. A warehouse loads data into a columnar, typed, indexed format for fast SQL and BI-tool access. Pattern: GCS = data lake (cheap storage), Snowflake = warehouse (fast analysis), the load task = the bridge.
Q Warehouse vs transactional database?›
OLAP (analytics — big scans/joins; Snowflake/BigQuery/Redshift/Synapse) vs OLTP (app reads/writes one row at a time; Postgres/Cloud SQL/RDS/Azure SQL). This project is analytics → warehouse. Native warehouse per cloud: GCP→BigQuery, AWS→Redshift, Azure→Synapse. Snowflake is cloud-agnostic → portable.
Q Snowflake's headline architecture?›
Separation of storage and compute — data in one layer; virtual warehouses provide independent, elastic compute against it; pay for each separately; multiple workloads hit the same data without contention. Three layers: storage, compute (warehouses), cloud services.
Q Does Snowflake enforce PRIMARY KEY?›
No — PK/FK are optimizer/documentation metadata, NOT enforced (only NOT NULL is enforced). Dedup must be handled in the load — which is exactly what the MERGE does.
Q Storage integration vs notification integration?›
Both are credential-less (Snowflake issues an SA identity you grant least-privilege; no keys exchanged). Storage integration = access to the bucket's files. Notification integration = connection to the bucket's events (a cloud queue, e.g. Pub/Sub).
Q Snowpipe vs scheduled COPY task?›
Snowpipe = continuous, event-driven (a cloud notification triggers the load). Scheduled task = polling/batch (runs COPY on a timer). This project uses the task after the Snowpipe bind failed. Same outcome (auto-load); different trigger model.
Q Internal vs external stage? TRANSIENT tables? Topic vs subscription?›
Stage: external → cloud storage you own (this project); internal → Snowflake-managed. TRANSIENT: no fail-safe/limited time-travel → cheaper; correct for throwaway staging. Pub/Sub: topic = broadcast channel (publishers send); subscription = listener (consumers read) — decouples producer (GCS) from consumer (Snowflake), which is why event systems scale.

✕ Debugging war stories

Week 4 in red are the headliners — the Snowpipe bind saga and the MERGE-on-a-dirty-target trap.

20Snowpipe Pub/Sub bind failure — the big one (unresolved → pivoted) — built the full path (topic, bucket notification, subscription, notification integration); CREATE PIPE … AUTO_INGEST=TRUE repeatedly failed with Could not monitor … PERMISSION_DENIED. Verified the SA had pubsub.subscriber (subscription + project + topic) AND pubsub.viewer (project), all readable via get-iam-policy; confirmed integration's subscription name + SA matched; confirmed subscription↔topic link; waited out propagation (incl. 10 min); recreated the integration (SA unchanged); confirmed personal Gmail (no org policy). All correct, still failed — root cause never found. Pivoted to a scheduled COPY task. Framing: "built Snowpipe end to end, hit a persistent cross-cloud IAM bind error, pivoted — same outcome; can discuss event-driven vs batch."
21Task SUCCEEDED but tables re-duplicated — counts ballooned (songs 2016/180). Cause: finals still held dupes from earlier manual FORCE=TRUE loads — MERGE dedups the source but can't dedup rows already in the target. Fix: reset to clean, then MERGE maintains cleanliness. Lesson: MERGE keeps a target clean only if it started clean.
17Wrong cloud at signup — first Snowflake trial defaulted to AWS_US_EAST_2. Caught via CURRENT_REGION() + the integration SA reading awsuseast2. Recreated on GCP_US_CENTRAL1 (matching the bucket) via a +alias email. Verify CURRENT_REGION() right after signup.
18Snowsight runs only the statement under the cursor — repeated "object does not exist" errors. Ctrl+A before Run to execute the whole worksheet.
19Regex PATTERN substring bug (recurred in SQL) — .*artists_.*\.csv also matched song_artists_…csv → artists loaded 1261 rows. Anchor with a path separator: .*/artists_.*\.csv.
22COPY load-history "0 files" confusion — re-running COPY returned 0 rows because COPY skips already-loaded files (idempotency by design). Diagnosed with FORCE=TRUE as a one-time tool; also revealed 10 days of autonomous runs.
23BEGIN…END task parse error — unexpected 'END'. Run the whole block as one unit; collapse each MERGE to a single line.
24Snowflake reuses the same SA per account — recreating the notification integration did NOT mint a new SA (stayed k26l…), so existing grants remained valid. Ruled out the "wrong SA after recreate" theory.
