01 Project Goal

An end-to-end, fully automated pipeline that pulls playlist data from the Spotify Web API daily, lands raw data in GCS, transforms it into normalized tables, and auto-loads it into Snowflake — zero manual steps after deployment — plus instrumentation and a daily email digest that reports what each run did. Built as a portfolio project for data-engineer / data-scientist interviews.

Ingestion note: the original goal named Snowpipe auto-ingest. That path was built end-to-end but hit a persistent cross-cloud IAM bind error (war story #20) and was replaced with a scheduled COPY task — the shipping design.

02 Architecture

Shipping ingestion state as of Week 5, plus the validated Week 6 analytics foundation.

Scheduler → extract → GCS raw → transform → GCS csv
   → external stage → load_spotify_task (COPY→MERGE→instrument→handoff)
   → clean tables
   → digest_task (independent 3:20 schedule, reads handoff) → email

Cloud Scheduler (2 AM) → extract-spotify → GCS raw_data/to_process/ → transform-spotify (Eventarc finalize event) → GCS transformed_data/ → Snowflake external stage → scheduled COPY task load_spotify_task (daily CRON 3 AM: COPY→staging → MERGE→finals → write load_log + pipeline_state) → clean deduped tables → independent digest_task (daily 3:20 AM: reads handoff, composes a status line) → email (SendGrid, Phase 3–4).

Week 6 analytics extension: Snowflake remains the source of truth. Curated views in SPOTIFY_DB.ANALYTICS will be published into BigQuery as a BI serving layer, and Looker Studio will connect to BigQuery natively. The BigQuery dataset and synchronization job have not been created yet.

Why the digest is a separate task, not a chained child: a task chained with AFTER load_spotify_task fires only when the parent succeeds — so on the one morning the pipeline breaks, no email is sent, which is exactly when you need it. An independent scheduled task fires regardless and reports SUCCEEDED / FAILED / PARTIAL / NO_RUN. Validated in practice by the Aug 19–24 outage (§W5.4).

W4 The load pattern (staging + MERGE)

Loading daily snapshots directly stacked ~20× duplicates (3,672 rows for 180 unique songs). The upsert pattern fixes it:

GCS CSVs → COPY into STAGING (all snapshots)
         → MERGE into FINAL (QUALIFY ROW_NUMBER() picks newest-per-key, upsert)
         → staging truncated next run

Bridge MERGE differs: composite match, SELECT DISTINCT, only WHEN NOT MATCHED (the two columns are the whole row). The task carries no FORCE=TRUE — it relies on COPY load-history to skip already-loaded files.

Week 5 — Instrumentation, Cost & Monitoring

Session 9 · Aug 20–25 · log tables, credit fix, digest task, outage & recovery, digest email shipped

W5 Instrumentation — what it accomplished

Turned a working-but-blind pipeline into an observable one. The load task now records what every run did, hands its identity to a monitoring task, and a daily digest reports status — and the whole thing survived a real multi-day GCS outage and recovered on its own, which the monitoring caught.

load_spotify_task (COPY→MERGE) → load_log (per-table insert/update counts, run_id, task_run_id)
                               → pipeline_state (run_id, completed_at, tables_loaded)   ← handoff
digest_task (independent 3:20) → reads pipeline_state + load_log → digest_log (status + subject) → [email]

W5 New log & state objects

  • load_log — one row per (table, run): log_id, table_name, rows_inserted, rows_updated, loaded_at, run_id (UUID, groups the 4 rows), task_run_id (per-MERGE LAST_QUERY_ID(), links to query_history). Written by INSERT … SELECT … FROM TABLE(RESULT_SCAN(LAST_QUERY_ID())) right after each MERGE.
  • pipeline_state — the load→digest handoff. One row per completed run: run_id, completed_at, tables_loaded. Written as the last statement of the load task — its existence is the "I finished" signal; a mid-flight abort writes no row.
  • digest_log — what the digest would email (Phase-1 staging before SendGrid): load_state (COMPLETE/PARTIAL/NO_RUN), load_run_id, tables_logged, new_rows, refreshed_rows, subject_line.
  • digest_task — independent scheduled task (CRON 3:20 AM), no AFTER. Reads the latest pipeline_state row, rolls up its load_log rows, classifies, composes a subject.

W5 The Aug 19–24 GCS outage — diagnosed by elimination, self-recovered

The pipeline began failing silently on Aug 19. Every COPY: Failed to access remote file: access denied — while LIST @spotify_stage succeeded. Snowflake could list the bucket but not read object contents.

Diagnosed by ruling everything out, in order:

  • Snowflake config — DESC INTEGRATION correct, integration exists. ✓ not it.
  • Bucket IAM — get-iam-policy: objectViewer bound, no condition, no deny. That role does include storage.objects.get. ✓ not it.
  • CMEK — top theory (LIST reads metadata; COPY must decrypt). buckets describe … encryption → null. ✗ ruled out.
  • Billing — $300/$300, 60 days, not suspended. ✗ ruled out.
  • Object readable? — gcloud storage cp of the exact file as myself succeeded (17.8 KiB). Only the Snowflake SA's read path failed.
  • Audit logs — empty (GCS data-access logging off by default).

Every layer checked out, yet COPY denied. The break coincided exactly with creating spotify_pubsub_int (the Snowpipe attempt) on Aug 19 09:27 — concurrent Pub/Sub/IAM changes. It then healed on its own: pipeline_state timestamps show the Aug 23 & Aug 24 01:00 scheduled runs both succeeded (tables_loaded=4) with no fix — a transient cross-cloud access failure that cleared after propagation. Confirmed with a manual EXECUTE TASK on Aug 24 → SUCCEEDED, 185 songs, four fresh load_log rows, digest read COMPLETE.

Framing: "A storage-integration COPY started failing with access-denied while LIST worked. I diagnosed by elimination — proved it wasn't the integration config, bucket IAM, encryption, or billing, and that the object was readable by me directly — narrowing it to a transient cross-cloud access failure during concurrent IAM changes. It self-recovered, which my pipeline_state timestamps confirmed. The lesson: a pipeline with no monitoring fails in the dark — had the digest been live, I'd have had an alert the first morning."

W5 Data-quality findings (from real data)

Dedup gap in transform. One songs CSV: 187 rows / 183 distinct song_ids — four tracks appear twice (identical but for added_at) because re-adding a track to a playlist makes a second entry. build_songs isn't deduping on song_id. MERGE collapses it downstream (finals stay clean), but the CSV presents song_id as a PK while holding duplicates.
Null-name rows. 3 rows carry empty name + duration_ms=0 (unavailable/local tracks). Flowed to Snowflake for weeks unnoticed — a null/blank check belongs in the digest.
File-count ≠ insert-count, by design. A CSV is a full snapshot (~187 rows) while "new rows inserted" is ~0–3. The digest reports rows-in-file / distinct-keys / inserted / updated per table so the difference is self-explaining rather than looking broken every morning.

W5 Debugging War Stories 25–33

25NOT-MATCHED-only MERGE has no "rows updated" column. The bridge capture failed with invalid identifier '"number of rows updated"' — a MERGE's result set only has columns for the clauses present, and the bridge has only WHEN NOT MATCHED. Fix: hardcode 0. Loud failure — named the line/column; ~20 min.
26CREATE OR REPLACE TASK always lands suspended. Sequence: REPLACE → RESUME → EXECUTE TASK. Verify with GET_DDL AND SHOW TASKS — not the absence of an error.
27Ctrl+A worksheet contamination. Ctrl+A selects the whole worksheet — smuggled a stray GET_DDL into the task body. Task defs in their own worksheet; verification queries in a scratch worksheet.
28Silent LET … := (SELECT …) binding failure — the nastiest. Returned null with no error; task SUCCEEDED, column silently null. Fix: inline LAST_QUERY_ID(). Loud failures cost an hour; silent failures ship wrong data. Verify the state, don't trust the silence.
29SYSTEM$TASK_RUNTIME_INFO('…GRAPH_RUN_GROUP_ID') is null under EXECUTE TASK. A key that only populates on the scheduled run can't be verified in dev. Chose LAST_QUERY_ID() (always available).
30Hand-transcribing an RSA key dropped 6 chars. The public key lost its trailing IDAQAB (exponent block) → Invalid Public key. Never hand-transcribe — pipe it: grep -v "PUBLIC KEY" key.pub | tr -d '\n'.
31JWT token is invalid = account identifier, not the key. First headless attempt passed the wrong account id; the connection reached Snowflake but the JWT issuer was rejected. A reached-but-rejected auth is an identifier problem, not network/key.
32printf secret upload failed silently in PowerShell. Unix command in PowerShell → not stored, and the key had been exposed. Use a temp file + Remove-Item; regenerate any key that touched a shell/chat.
33gen2 Cloud Function needs run.invoker for OIDC. Scheduler → authenticated function returned 403 until the SA got run.invoker on the Cloud Run service (gen2 functions ARE Cloud Run). --no-allow-unauthenticated means even your own scheduler must be granted invoke.

DecisionChoiceReason / trade-off
System of recordSnowflakeExisting pipeline, normalization, and data-quality logic terminate there. BigQuery is a serving copy, not a second source of truth.
BI connectionLooker Studio → BigQuery nativelyAdds market-relevant BigQuery experience and keeps dashboard queries off the ingestion warehouse.
Published objectsCurated analytics models, not raw tablesConsumers should not rebuild bridge joins, grain rules, or duration/release-year calculations.
Dashboard behavior on sync failureRemain available with stale dataAvailability is preferred over a blank dashboard. Show last_successful_refresh_at and a stale warning.
Automatic retryNo automatic retry initiallyFail once, alert by email/indicator, investigate, fix, and manually rerun. This avoids repeated bad loads and retry storms while the workflow is small.
IdempotencyBatch ID + deterministic keys + MERGE/atomic publicationA batch ID provides lineage, while the business key prevents duplicate target rows if the same batch is rerun.
Current implementation strategyAtomic full refresh for the tiny curated modelsAt 194 songs, it is simplest to validate. Load staging tables, validate them, then replace/publish so failure leaves the previous good tables available.
Scale strategyIncremental MERGE when operational thresholds justify itAt 100M rows with 1M daily changes, only 1% changes; rewriting 99M unchanged rows wastes scan, transfer, time, and money.

Measurable triggers for moving from full refresh to incremental:

  • Full refresh no longer completes inside the agreed load window or dashboard freshness SLA.
  • Daily bytes scanned/transferred or compute cost exceeds an agreed budget while the changed-row percentage stays low.
  • Refresh volume creates operational side effects such as load failures, quota pressure, long table unavailability, or excessive downstream cache invalidation.

W6 Critical model limitation and future fact table

Current limitation: RAW.SONGS represents one row per unique song retained across observed loads. It does not prove exact current playlist membership. The latest file can contain the same song more than once, while the MERGE target can retain a song removed from the latest playlist.

Therefore the first dashboard must be labeled “Spotify playlist catalog observed by the pipeline”, not “exact current playlist.”

A future membership fact should use this grain:

PLAYLIST_ID + SNAPSHOT_ID + POSITION → one playlist occurrence
columns: playlist_id, snapshot_id, position, song_id, added_at, extracted_at
  • snapshot_id is Spotify’s source version identifier.
  • extracted_at records when the pipeline observed that version.
  • position distinguishes repeated occurrences of the same song.
  • This enables additions/removals between snapshots, current membership, position change, and playlist growth analysis.

W6 Real errors, root causes, fixes, and prevention

34Join fan-out inflated “final” counts. A full-outer-join profiling query returned 2,784 songs, 1,978 albums, 2,907 artists, and 6,749 bridge rows. Those were not final-table counts; joining one-to-many staging snapshots multiplied rows. Fix: profile each table independently at its declared key/grain before joining. Prevention: state the expected grain beside every validation query.
35LIST timestamps sorted by weekday text. Snowflake returned last_modified as text, so DESC ordering produced weekday-alphabetical results rather than chronological results. Fix: remove “ GMT” and parse with TRY_TO_TIMESTAMP_NTZ(..., 'DY, DD MON YYYY HH24:MI:SS'). Prevention: inspect types before ordering date-looking values.
36RESULT_SCAN(LAST_QUERY_ID()) scanned the wrong result. A five-row SELECT was run after LIST, so LAST_QUERY_ID pointed to that SELECT—not the LIST output. Fix: run LIST immediately before RESULT_SCAN or capture the required query ID explicitly. Prevention: treat LAST_QUERY_ID as an exact statement pointer, not session memory.
37Duplicated external-stage path returned zero rows without an error. The stage URL already ended at transformed_data/; querying @stage/transformed_data/file repeated the folder. Fix: use @SPOTIFY_DB.RAW.SPOTIFY_STAGE/songs_20260825_070027.csv. Prevention: validate source-row count > 0 before publication; retain the previous target and alert if validation fails.
38Entity deduplication hid playlist occurrences. Three songs occurred twice in the latest snapshot with different added timestamps; MERGE correctly produced one entity row but could not preserve both playlist positions. Fix requires a separate occurrence fact keyed by playlist + snapshot + position—not weakening the SONGS primary key.
39Learning workflow correction in Git. Three remotely prepared implementation commits were reverted so the user could implement and understand each change personally. W6 Interview questions and model answers

Data modeling
Q Why can a table have a valid primary key but invalid foreign-key relationships?›
A primary key proves only that rows in that table have unique, non-null identifiers. A foreign key tests whether a referenced parent exists in another table. A SONG row can have a unique SONG_ID but an ALBUM_ID that has no matching ALBUM row. In standard Snowflake tables, PK/FK constraints are generally informational rather than enforced, so the pipeline must validate referential integrity.
Q Why did joining the staging tables inflate the counts?›
Each staging table contained many historical full snapshots. Joining repeated rows across one-to-many relationships created a multiplicative fan-out. Correct profiling starts by counting each table at its declared key, then joins only deduplicated inputs when relationship analysis is required.
Q Why can’t the top-ten artist counts be divided directly by 194 songs?›
Songs can have multiple artists. The 490 bridge rows are artist-song relationships, so artist song counts overlap. Summing artist counts does not produce distinct songs. Use a ranked bar chart or calculate a clearly defined relationship share.
Q What is the difference between snapshot_id and extracted_at?›
snapshot_id is the source-system version of the playlist; extracted_at is when this pipeline observed it. The same snapshot on two extraction dates means the playlist did not change between observations.
Architecture and reliability
Q Why keep Snowflake as source of truth while serving Looker Studio from BigQuery?›
Snowflake already owns the ingestion, normalization, and validated business logic. BigQuery is a purpose-built serving copy for native Looker Studio access and portfolio experience. Declaring one source of truth prevents conflicting corrections and definitions across warehouses.
Q What happens if Snowflake→BigQuery synchronization fails?›
The dashboard keeps the last successfully published tables available, shows the last successful refresh time, and marks them stale. The job fails and alerts; a developer investigates and manually reruns it. A failed batch must never replace the last known-good target.
Q How do you prevent a rerun from duplicating BigQuery rows?›
Assign a batch ID for lineage, validate deterministic business keys, and publish with an idempotent MERGE or atomic staged replacement. Batch ID alone records which run produced a row; uniqueness/MERGE logic is what prevents duplicate business records.
Q Why not full-refresh 100 million rows when only 1 million change daily?›
Only 1% changes. Incremental loading processes that 1% instead of repeatedly scanning, transferring, and rewriting the unchanged 99%, improving cost and the chance of meeting the freshness SLA.
Q What decision does the artist-concentration dashboard support?›
A playlist analyst can determine whether a few artists dominate the catalog and decide whether to diversify with underrepresented artists, subject to the playlist’s audience and content strategy.
